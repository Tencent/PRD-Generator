# 修改与评审修订

已有 PRD 项目上的任何修改（增删改页面、改规则、评审反馈）都走本流程。**核心：先改 spec，再让脚本重新派生图和表，最后才改正文。**不手改 PNG、不手改清单表、不手写流转行。

## 1. 流程

```
定位 → 判断类型 → 先过地图闸门（涉及页面/流转变化时）→ 改 → 重新派生 → 闸门自检并修 → 汇报
```

| 步骤 | 做什么 |
|---|---|
| ① 定位 | `prdkit.py where` 找到项目；读 PRD 与 `spec/`；列出现有章节、页面、截图 |
| ② 判断类型 | 见 §2；确定影响范围。**动手前先用一句话告诉用户**：`我判断这属于「{类型}」，会改 {文件/页面}，约 {x} 分钟。这样处理可以吗？` |
| ③ 版本策略 | 迭代项目默认**另存新版本目录**，旧版本保留；只有用户明确说“直接改原文档”才原地改。新目录若是从旧版本复制而来，先 `prdkit.py demo reset`（Demo 回到“待发布”），再 `links --apply`，避免 PRD 继续指向旧版本的在线 Demo |
| ④ 修改 | 按 §3 顺序，由上游往下游改 |
| ⑤ 重新派生 | 页面或流转变了就重新截图、流程图、清单、流转行（§3） |
| ⑥ 闸门 | 跑对应闸门（`check map / prototype / flow / prd`），按 `quality-gates.md` 修复循环，0 错误才汇报 |
| ⑦ 汇报 | 变更摘要 + 自检结果 + 发布提醒（§5） |

## 2. 修改类型与影响

| 类型 | 例子 | 需改 | 需重做 |
|---|---|---|---|
| 文案/规则微调 | 改某条 BR 的数值、某个提示文案 | PRD；原型里同一处文案同步 | 文案在页面上可见 → 重新截图 |
| 局部页面调整 | 加一个字段、改按钮 | 原型页面 + PRD 元素表 + 交互规则 | 该页截图；流转没变则不动图 |
| 新增页面/弹窗/状态 | 加“收藏页” | `screens.json`、flows、原型、PRD 小节 | 截图、章级图、整体图、清单、流转行（相邻页面也要更新）、`index` |
| 删除页面 | 去掉某弹窗 | 同上，删除对应小节与截图引用 | 同上 |
| 流转变化 | 改跳转关系 | flows | 流程图、清单、**相邻页面的流转行** |
| 章节重排 | 调整章序 | `chapters`、PRD 标题与章号 | 章号相关的图名、交叉引用 |
| 全局调整 | 改目标用户、产品类型 | 视情况重走主流程 | 全量 |
| 换风格/主色 | “改成毛玻璃”“主色换红” | `style apply`（不改 spec 页面） | `shot`、`flow` 全量 |

## 3. 改的顺序（上游 → 下游）

1. **spec**：`spec/screens.json`、`spec/flows/*.json`
2. **原型**：`prototype/pages/*.html`；页面有增删时 `prdkit.py index`
3. **派生物**（全部用命令，不手改）：
   ```bash
   python3 scripts/prdkit.py shot              # 截图（可 --only 指定页面）
   python3 scripts/prdkit.py flow              # 流程图 + 几何自检
   python3 scripts/prdkit.py flow --table      # 页面清单，整表替换
   python3 scripts/prdkit.py flow --transit    # 流转行草稿，覆盖对应行
   python3 scripts/prdkit.py links --apply     # 关联原型与附录 B
   ```
4. **PRD 正文**：元素表、交互规则、业务规则、数据字段、异常、埋点；**修订说明**追加一行
5. 已记录在线 Demo 时：原型有改动，请用户把最新的 `prototype/` 重新托管（可用 `demo pack` 打包），地址变了就 `demo online <新地址>`，再 `links --apply`；新版本目录则按 §1 ③ 重置后，按 `SKILL.md` §4 重新处理 Demo

## 4. 评审反馈怎么处理

1. 逐条列出反馈，标出**每条对应的位置**与**处理方式**：采纳并修改 / 不采纳并说明理由 / 需要用户决策（不要替用户拍板）。
2. 反馈涉及多页的，先出清单让用户确认，再统一修改，避免“改一条、重跑一遍”。
3. 修订说明表追加一行：**改了什么、为什么**（如“借用时长上限 7 天 → 14 天，评审意见：大件工具周期更长”），不写“优化文案”这类空话。
4. 改动涉及**范围**时，复核 M-33/M-34（范围与原型一致、规则与元素有落点），见 `qa-semantic.md`。

## 5. 汇报格式（精简）

```
✅ PRD 修改完成（{版本}）

改了什么：
  1. …（标位置）
  2. …
受影响：PRD / 原型页面 / 截图 {N} 张 / 流程图 {3.1、3.0} / 清单 / 流转行

自检：已通过{有重要修正时：，其中 …}。（说“看质量明细”可展开）

📤 发布提醒：{PRD 已修改。如之前已记录在线 Demo，原型有改动时线上版本不会自动同步，需要重新托管最新的 prototype/。要现在处理吗？}
```

**必须包含“发布提醒”**：修改后线上版本与本地不一致，是最常见的遗漏。Demo 的话术沿用 `SKILL.md` §4。

## 6. 修改闸门（只查受影响部分，但脚本不区分，直接全跑更省事）

| 改了什么 | 至少跑 |
|---|---|
| 只改文字 | `check prd` |
| 改了原型页面 | `check prototype` → `check flow` → `check prd` |
| 改了页面登记或流转 | `check map` → `check prototype` → `check flow` → `check prd` |
| 换风格主色 | `check style` → `check prototype` → `check flow` → `check prd` |

最后统一 `prdkit.py check all` 过一遍最稳。止损规则同 `quality-gates.md`：同一错误连续 2 次未消失，退一层重新分析，不要再用同样的办法重试。
